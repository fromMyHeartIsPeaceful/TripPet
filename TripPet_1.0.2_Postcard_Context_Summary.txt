============================================================
一、任务背景
============================================================

本次任务是在 TripPet 当前 1.0.1 基础上，实现 1.0.2 明信片系统 MVP。

用户给出的最终规划要点：

1. 1.0.2 先做完整闭环，不追求内容规模。
2. 首发只做 3 只小动物：
   - cat：墨迹，猫
   - dog：汤圆，小狗
   - rabbit：灯灯，兔子
3. 用户可见文本必须统一为“汤圆”，不能再出现“糖圆”。
4. 首发目的地为 3 个国外城市：
   - 巴黎 fr_paris
   - 雷克雅未克 is_reykjavik
   - 里斯本 pt_lisbon
5. 不加入国内城市、美国城市、其他东亚城市。用户特别指出“上海替换为其他国外城市，但是不要美国和其他东亚城市”，最终选择里斯本。
6. 明信片文字继续由 SwiftUI 渲染，禁止烘焙进图片。
7. 1.0.2 明信片不展示小动物自拍。
8. 动物感通过标题、正文、关系记忆体现，不通过明信片视觉自拍体现。
9. 美术先只做 1 套通用模板，跑通逻辑闭环后再扩展动物姿势、多模板、贴纸等。
10. 新模板需要扩大地点风景展示区，淡化和地点风景无关的装饰。

核心实现目标：

- 资源层：新增大风景通用明信片模板、里斯本风景、里斯本邮戳、里斯本路线图。
- 内容层：扩展 manifest，包含动物 profile、目的地 scenes、叙事模板等。
- 数据层：扩展 Animal、Trip、Postcard，新增 AnimalRelationshipMemory。
- 逻辑层：送出旅行时创建 postcardPlan，到期按计划投递，长途最多 2 张卡。
- 叙事层：新增本地确定性 PostcardNarrativeEngine，不联网、不服务端、不临时编造地点事实。
- UI 层：邮箱投递反馈、未读优先、Root Tab badge、明信片详情大风景布局、打开标记已读、收藏页沿用已读展示。
- 测试层：补充 1.0.2 核心规则单元测试，保持 iPhoneOS build 和 Simulator tests 通过。


============================================================
二、总体实现思路
============================================================

本次采用“先闭环、后扩展”的实现策略。

1. 内容范围收窄

只保留 3 只可旅行动物和 3 个目的地，避免一次性做大规模地点库、动物姿势和模板系统。这样可以优先验证：

- 派行动物是否正确轮换。
- 每只动物是否能拥有自己的 active wish。
- 旅行是否能提前生成 postcardPlan。
- 邮箱是否能按到期时间投递明信片。
- 明信片详情是否能用统一模板和地点风景完成展示。
- 已读、未读、收藏、关系记忆是否能持久化。

2. 美术资源先通用化

根据用户要求，1.0.2 不再给明信片做动物自拍视觉。因此资源设计变成：

- 通用明信片模板：postcard_template_landscape_v102
- 地点风景主视觉：destination_*_line
- 邮戳：stamp_*
- SwiftUI 渲染标题、subtitle、正文、日期

这样既节省动物姿势资源，又能把明信片第一眼重点转向地点风景。

3. 数据兼容优先

在 domain model 中新增字段时都提供默认值，避免旧初始化点大量破裂。
SwiftData 持久化模型中，对 1.0.2 新增字段使用 optional 存储和读取兜底，降低从 1.0.1 本地数据库升级时的风险。

4. 叙事引擎本地确定性

PostcardNarrativeEngine 不联网，也不在运行时随意编造事实。它只从 manifest 里预审过的 animal profile、destination scenes、templates 中选择素材。

最开始实现中曾使用 Swift 的 String.hashValue 做稳定选择；后续发现 hashValue 跨进程不保证稳定，于是改成固定 DJB2 风格 stableHash，保证同样输入在不同启动中也能稳定选择。

5. 新旧系统兼容

旧 postcard 仍可展示。
animalAssetName 字段仍保留，但 1.0.2 明信片详情页不再渲染动物自拍。
旧 postcard_template_classic 保留为 fallback，不作为 1.0.2 默认体验。

    ticketCount: Int,
    date: Date = Date(),

    scheduler: PostcardScheduler = PostcardScheduler()

新行为：

- 送票时确定当前动物。
- 获取或创建当前动物的 wish。
- 查找目的地。
- 调用 scheduler.makePostcardPlan(for:departedAt:) 创建 postcardPlan。

- 更新小屋派行状态。

- 如果 trip.postcardPlan 为空，沿用旧逻辑：到期生成一张旧式 postcard 并完成 trip。
- 如果 trip.postcardPlan 非空，按 revealedPostcardCount 取下一张计划。
- 到期后使用 PostcardNarrativeEngine 生成 postcard。
- 插入 mailbox。
- revealedPostcardCount += 1。
- 更新 AnimalRelationshipMemory。
- 如果 plan 全部投递完，trip 才 completed，wish 才 completed。

约束：

- 同一 trip 不重复投递同一 sequence。
- long trip 两张卡由 plan 保证不同 sceneId、postcardType、microArc。
- 一次旅行最多 2 张明信片。

============================================================

主要文件：

PostcardScheduler 新增 makePostcardPlan(for:departedAt:)。

规则：

1. short
   - 1 张
   - dueAt：departedAt + 1 天
   - postcardType：daily_observation
   - fallbackArc：动作型
   - emotionalWeight：0

2. standard
   - 1 张
   - dueAt：departedAt + 2 天
   - postcardType：personality_reaction
   - fallbackArc：选择型
   - emotionalWeight：1

3. long
   - 2 张
   - 第 1 张：
     - dueAt：departedAt + 2 天
     - postcardType：daily_observation
     - fallbackArc：旁观型
     - emotionalWeight：0
   - 第 2 张：
     - dueAt：departedAt + 4 天
     - postcardType：motif_echo
     - fallbackArc：回声型
     - emotionalWeight：2
   - 尽量选择不同 sceneId。

PostcardScheduler.makePostcard 兼容旧逻辑，同时现在会填入 1.0.2 metadata 和默认模板：

- templateAssetName 使用 destination.postcardTemplateAssetName ?? postcard_template_landscape_v102

PostcardNarrativeEngine：

输入：

- trip
- planItem
- animal
- destination
- narrative
- memory
- recentPostcards
- date

输出：

- 完整 Postcard

生成流程：

1. 按 animal.profileId 找 narrative profile。
2. 按 planItem.sceneId、postcardType、animalAffinity、recentSceneIds 选择 scene。
3. 按 postcardType 和 microArc 找 narrative template。
4. 计算 emotionalWeight。
5. 从 animal motifs 中选择 motif，并避开 recentlyUsedMotifs。
6. 从 scene 中选择 object/action/sensory。
7. 从 reactionLines 或 relationshipLines 中选择 reaction。
8. 根据 microArc 生成 body。
9. 填入 metadata。

叙事注意点：

- 不联网。
- 不访问服务端。
- 不临时编造地点事实。
- 只使用 manifest 中已整理的 scene、object、action、sensory、animal profile。
- 使用 stableHash 替代 Swift String.hashValue，避免跨进程不稳定。

当前 bodyText 支持的 microArc：

- 误会型
- 旁观型
- 回声型
- 选择型
- default 动作型/其他

标题格式：

- "\(animal.name)寄来的\(destination.displayName)明信片"

因此 dog 生成标题会是：

- 汤圆寄来的里斯本明信片

============================================================
十六、重要设计取舍
============================================================

1. animalAssetName 没有删除

原因：

- 兼容旧 postcard 数据。
- 避免持久化和旧 UI 初始化点破坏。

但 1.0.2 明信片详情页不再展示 animalAssetName。

2. 只做 1 套模板

原因：

- 用户明确要求先通用模板，节省美术资源。
- 当前重点是验证闭环。

后续可按地点/动物/关系阶段拓展多模板。

3. 里斯本作为第三目的地

原因：

- 替代上海。
- 非中国、非美国、非其他东亚。
- 视觉上可与巴黎、雷克雅未克形成差异：坡道、旧街、白墙、浅陶土、海风。

4. 长途两张卡只给雷克雅未克

原因：

- 计划中要求：
  - 里斯本 short：1-2 天，1 张
  - 巴黎 standard：2-3 天，1 张
  - 雷克雅未克 long：3-5 天，2 张

5. 叙事引擎暂不做复杂自然语言生成

原因：

- MVP 阶段稳定性优先。
- 避免联网和临时编造地点事实。
- 文案由 manifest 中预审素材组合，便于人工终审和后续调优。

6. recentlyUsedMotifs 当前更新为 postcard.microArc

现状：

- updateRelationshipMemory(afterSending:) 当前把 postcard.microArc append 到 recentlyUsedMotifs。

注意：

- 这能起到部分“近期叙事机制冷却”的效果，但严格来说不是 motif 本身。
- 后续如果要更精确，应把 selected motif 写入 Postcard metadata，或新增 motif 字段，再更新 memory.recentlyUsedMotifs。
